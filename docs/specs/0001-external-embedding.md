# 外部嵌入服务与无 Ollama 运行

状态：待实施。日期：2026-11-16。

## Problem Statement

这套系统要跑完整的知识库链路，必须在本机起一个 Ollama 提供嵌入向量。聊天模型已经能走外部网关，嵌入这一条还没有解耦：

- `.env.example` 的默认值指向 `localhost:11434`，新拉仓库的人不装 Ollama 就走不完上传与检索。
- 嵌入服务不在线时，`/api/research/*` 的检索直接抛错，整条研究以失败结束；`/api/agent/*` 会退到稀疏检索，两条路径行为不一致。
- 换嵌入服务会让已有索引全部失效，而唯一的重灌命令只处理资料目录里的文件，会把已上传文档的向量一起清掉，事后无法从数据库里算回来。
- 「本部署不使用 Ollama」这件事没有任何检查，配错了要等第一次检索才暴露。

免费嵌入服务都可以直接调用，问题不在能不能用，在于配置面、失败行为和索引迁移没有一处理顺。

## Solution

把嵌入服务变成可配置的外部服务。默认接 Voyage AI，填一个 `EMBEDDING_API_KEY` 就能在没有 Ollama 的机器上完成上传、检索与出报告。Jina AI 作为同维度的备选，换家只改三个环境变量。

嵌入服务不可用时，检索退到稀疏检索，报告正文写明「本轮仅使用稀疏检索」并附降级原因，事件流同步记录。

换嵌入服务后用一条命令重灌全部语料：资料目录与已上传文档一起处理，不再丢数据。

启动时按开关检查本部署不依赖 Ollama，并把实际生效的嵌入服务地址打进启动日志。

## User Stories

1. 作为部署这套系统的开发者，我想在一个没装 Ollama 的机器上只填一个嵌入服务的 key 就把系统跑起来，以便不为了跑通知识库而先装上一套本地模型运行时。
2. 作为部署这套系统的开发者，我想让 `.env.example` 默认指向外部嵌入服务，以便新拉仓库的人照 README 操作就能跑通，不必先改配置。
3. 作为部署这套系统的开发者，我想用 `EMBEDDING_PROVIDER` 切换 voyage、jina、openai、ollama 四家中的一家，以便换服务时不需要改代码。
4. 作为部署这套系统的开发者，我想在同一维度下换家只需要改 key、模型名与地址三项，以便换服务不会有额外的索引维度麻烦。
5. 作为部署这套系统的开发者，我想在启动日志里看到实际生效的嵌入服务地址与模型名，以便确认请求打到哪家。
6. 作为部署这套系统的开发者，我想在开启「不使用 Ollama」开关时，配置里仍然指向 Ollama 就直接启动失败，以便配错立刻暴露。
7. 作为部署这套系统的开发者，我想让这条检查只在开关打开时生效，以便保留 Ollama 作为可选路径。
8. 作为部署这套系统的开发者，我想在没有 key 时启动仍然成功、只在检索时报出明确原因，以便先跑通其他链路。
9. 作为研究者，我想让知识库检索在嵌入服务不可用时自动退到稀疏检索，以便服务抖动不会让整条研究失败。
10. 作为研究者，我想在退到稀疏检索时报告照样产出，以便还能拿到能拿到的结论。
11. 作为研究者，我想在报告末尾看到「本轮仅使用稀疏检索」的说明与降级原因，以便知道这一轮结论的证据强度不同。
12. 作为研究者，我想让两条研究入口（`/api/research/*` 与 `/api/agent/*`）在降级时行为一致，以便换入口不会得到不同的失败表现。
13. 作为研究者，我想让稀疏检索命中的片段照常带来源编号，以便引用链不断。
14. 作为研究者，我想在检索彻底失败时仍然按原有方式失败，以便数据库不可用这类问题不会被伪装成降级。
15. 作为维护者，我想用一条命令重灌全部语料，以便换成外部嵌入服务后所有文档都能被检索到。
16. 作为维护者，我想让重灌同时处理资料目录与已上传文档，以便上传过的文档不会在重灌后消失。
17. 作为维护者，我想在重灌前看到新旧索引配置的差异，以便知道这次重灌会清掉什么。
18. 作为维护者，我想在索引配置不匹配时看到明确的重新摄取提示，以便知道该跑哪条命令。
19. 作为维护者，我想在重灌完成后看到文档数、片段数与耗时，以便判断这次操作是否完整。
20. 作为维护者，我想手动触发一次嵌入服务探测并看到实际维度与期望维度，以便配置错误能被立刻定位。
21. 作为维护者，我想让探测只在显式请求时执行，以便 API 启动不依赖外部服务在线。
22. 作为维护者，我想让 429 与 5xx 做有限次退避重试，以便免费额度限速不会变成随机失败。
23. 作为维护者，我想让 4xx 之类的确定性错误立即失败并带上原始状态码，以便不必等重试。
24. 作为维护者，我想让查询与文档分别用不同的任务类型嵌入，以便检索质量等于所选模型本身的水平。
25. 作为维护者，我想让 Ollama 分支忽略任务类型参数，以便保留本地路径时不报错。
26. 作为审计者，我想在事件流里看到一次降级事件，以便事后判断某份报告的证据来源。
27. 作为审计者，我想让验收证据（真实报告与启动日志）随代码提交，以便回看「无 Ollama 跑通」的实证。
28. 作为学习者，我想让术语表把「嵌入服务」「索引配置」「降级检索」这几个词固定下来，以便文档与代码用同一套说法。
29. 作为学习者，我想有一份决策记录说明为什么保留 Ollama 代码却默认不依赖它，以便后来的人不必重新推演。
30. 作为开发者，我想在改动后仍能跑通全量类型检查、lint、格式检查与测试，以便这次改动不引入回归。

## Implementation Decisions

**配置面**

- 嵌入服务的提供方枚举从 `ollama | openai` 扩展为 `ollama | openai | voyage | jina`。聊天侧的提供方类型不变。
- 新增 `EMBEDDING_API_KEY`，供 voyage 与 jina 使用；`OPENAI_API_KEY` 只服务 openai 分支。密钥只出现在 API 进程环境里。
- `EMBEDDING_BASE_URL` 保持可选，缺省值按提供方给出：voyage 为 `https://api.voyageai.com/v1`，jina 为 `https://api.jina.ai/v1`，openai 为官方地址，ollama 为 `http://localhost:11434`。
- `EMBEDDING_MODEL` 保持必填，不设隐式默认；示例配置填 `voyage-4`。
- `EMBEDDING_DIMENSIONS` 固定 1024，仍做严格校验。
- `.env.example` 默认改为 voyage，Ollama 相关段落移入注释并注明为可选路径。

**嵌入适配**

- `Embedder` 接口的 `embed` 增加第二个参数 `kind: "query" | "document"`。摄取、上传、更新文档传 `document`，检索与知识库搜索传 `query`。Ollama 分支忽略该参数。
- 新增一个 OpenAI 兼容的嵌入适配器，承载 openai、voyage、jina 三家的传输，按提供方映射附加字段：voyage 用 `input_type`、jina 用 `task`，维度参数分别映射为 `output_dimension` 与 `dimensions`，openai 不附加任何字段。
- 三家统一 `truncation` / `truncate` 显式关闭，超长输入报错而不静默截断。
- 认证只用 Bearer；不引入第二种认证头。
- 适配器接受可注入的 `fetchImpl`，与既有模型适配器保持一致。
- 关闭 SDK 自身的重试，改为外层有限重试：仅 429 与 5xx 重试，最多 2 次，尊重 `Retry-After`，单次等待设上限；其余错误立即失败并把状态码写进错误信息。
- 维度与数值校验沿用现有规则，错误信息里带上实际维度与期望维度。

**检索降级**

- `RagService` 的两个检索入口（单查询检索与统一知识库检索）在嵌入调用失败时改为：记录降级原因，只走稀疏检索并返回结果，而不是抛出检索错误。
- 检索结果对象增加 `degraded` 与 `degradedReason` 两个字段。
- 稀疏检索同样无结果时，按「无相关证据」返回空集合并保留 `degraded` 标记，不伪造命中。
- 数据库不可用这类非嵌入故障仍然抛出检索错误，保持既有失败语义。
- `LocalRetriever` 这种只返回命中片段的接口形状保持不变，供联网检索实现使用。
- agent 运行时里原有的「稀疏检索重试」分支在服务层支持降级后成为冗余，移除该分支；工具层的失败分类保留。

**报告与事件**

- 报告正文末尾增加一段固定标题的「检索说明」，写明本轮仅使用稀疏检索及降级原因。该段落按与原报告去重的方式追加，重复生成不叠加。
- 新增 `RETRIEVAL_DEGRADED` 事件，携带降级原因与检索策略。事件类型加入事件契约文档。

**索引重灌**

- 新增一条重灌命令，顺序为：先按资料目录全量替换索引，再从已上传文档重建片段与向量并追加到同一索引配置下。
- 仓储层新增「列出全部已存文档」的方法，供重灌读取文档全文。
- 重灌前打印新旧索引配置的摘要，重灌后打印文档数、片段数、降级次数与耗时。
- 不自动触发重灌；索引配置不匹配时的报错文案指向这条命令。

**健康检查与启动**

- 知识库健康检查增加一个可选探测参数，触发时对嵌入服务做一次真实请求，返回实际维度、期望维度与模型名。
- 新增纯函数 `assertNoOllama(env)`：开关打开时校验聊天与嵌入两处提供方都不是 ollama，否则抛出带明确信息的错误。
- 启动日志增加生效的嵌入提供方、模型名与地址。

**文档**

- 新增 `GLOSSARY.md`，固定「嵌入服务」「索引配置」「降级检索」「重灌」四个词。
- 新增决策记录 `docs/decisions/0004-external-embedding.md`，说明默认接外部嵌入、保留 Ollama 代码路径、以及采用启动断言的理由；该记录接替 ADR 0002 中关于 Ollama 的默认条款。
- 更新 README 与 HKUST 网关文档里「RAG 仍使用 Ollama」的表述。

## Testing Decisions

好的测试只验证外部行为：给定输入与注入的传输层，得到什么结果、发出什么请求、产生什么可观察输出。不断言内部私有方法、不断言实现顺序、不用 mock 替换被测模块本身。

五个测试切面，四个沿用既有模块：

1. 嵌入适配器：通过注入的 `fetchImpl` 构造，断言请求体的字段映射（query 与 document 分别映射到 `input_type` 与 `task`）、超长输入报错、429 与 5xx 的重试次数与最终结果、4xx 立即失败、维度不匹配的错误信息。先例是模型适配器测试里注入 fetch 断言请求体的写法。
2. 检索服务：用 PGlite 存储与可注入行为的假嵌入器，断言嵌入失败时降级返回稀疏命中的结果、`degraded` 标记、数据库故障仍然抛错。先例是知识库测试里的确定性假嵌入器。
3. 重灌：在同一个 PGlite 库上先建旧索引、再换成新嵌入器、跑重灌、断言资料目录与已上传文档都能被检索到，且文档行没有被删除。先例同上。
4. 研究循环：用假模型与一个嵌入必然失败的检索器，断言收到 `RETRIEVAL_DEGRADED` 事件、报告含「检索说明」段落。先例是研究循环测试里按序出队的假模型。
5. 启动断言：纯函数级别的输入输出测试。先例是模型配置测试直接调用配置读取函数。

验收证据：一份真实运行产出的报告文件与一段启动日志，放在 `docs/verification/` 并随代码提交。

## Out of Scope

- 删除 `ollama` 依赖包，或把聊天侧的提供方类型收窄。
- 完全不配任何嵌入服务就能出报告的「零 key 模式」；`rag_chunks` 的向量列仍为必填。
- 多个嵌入服务同时并存，或按项目分配不同嵌入配置；索引仍是全局单例。
- 多 key 轮换与额度自动切换。
- 聊天模型侧的改动，包括原生工具调用。
- MCP、A2A 协议层的改动。
- 浏览器旧客户端的改动。
- 自动重建索引、后台重灌与进度查询。
- 面向大语料的并发批量嵌入与断点续传。

## Further Notes

索引是全局单例，一次只能有一套嵌入配置；换配置必然整套重灌，这一点在重灌命令的提示里要写清楚。

语料规模上限是 30 份、每份 24KB 的 Markdown。全量重灌一次约 20 万 tokens，Voyage 每账户前 2 亿 tokens 免费，够用约一千次。Jina 的免费额度官方页面没有给出数字，作为备选而非默认。

Voyage 官方没有声明 OpenAI schema 兼容，只有响应形状一致；Jina 官方明确声明兼容。两家共用同一个适配器，差别只在附加字段的映射上。

验收标准：在没有安装 Ollama 的机器上全新克隆、只配外部 key，走完上传、检索、完整报告与导出；一次自动测试证明无 Ollama 配置时启动断言通过；报告与日志留档。
